# PR First

The pull request is where work is proposed, argued and recorded — not a formality wrapped round a branch that was already finished.
It stands in for the tracker a team would have. A Portfolio with no Jira has nowhere else that is searchable, that a Challenge can arrive in from outside, and that is already attached to the change rather than pointing at it across a system boundary.
It is also the only Collaboration point available to a solo. Agents in separate sandboxes share no filesystem, no shell and no conversation. What they share is the pull request — which is why review and disagreement have to land there, and not in a transcript only one of them can see.
It is also where a **Handoff** happens — the seam where one Job stops and another takes the same Challenge up. Collaborations here are sequential, one Job at a time, each aware only of its own Agency, and what crosses the seam is only what the pull request and the branch hold. A handoff is a **semaphore, not a message**: GitHub's review request names a successor and is a state GitHub holds and reports, so an arriving Job finds its work by asking what has been requested of it rather than by reading anything. A review can only be requested of an account, which is what the Role accounts are for: `.meta/say/move request-review <n>` names the next Role's, and the arriving Job asks GitHub what has been requested of its login.
It is where **work noticed and not done** goes, as a linked Issue. A long run ends with things seen and left alone — out of scope, or a reasonable next step — and they are delivered in a closing summary, which is the one place with no persistence at all. Collecting them into a file instead fails four ways: a file has no open and closed, so a line removed is indistinguishable from a line resolved, abandoned or tidied; the item loses the work it was noticed during, so nobody can tell later whether it still applies; appending a line is free and invisible, so the file only grows; and flushing it means one unscoped batch of unrelated items sharing no context, which is the worst possible shape to hand an agent and the reason that follow-up run is expensive.
A linked Issue answers each. It has state, it carries a backlink to the work that found it, its title is read by someone, and it can be picked up alone.
The prior question is whether to eject it at all. An Issue is for work that is **not being done now** — out of scope, owed a decision, larger than the change that found it. It is not a place to put a fix already within the branch's reach. Ejection costs a Job's start, and that start costs about the same whether what waits is three lines or three hundred: a Job arriving holds nothing and loads the problem from the record, which is the expense the four failures above were weighed against and is paid here too. Where the fix is mechanical and the branch can already reach it, the cheaper act is the fix — in a commit of its own, saying what it is, so the diff still reads as one change with an Incidental Commit beside it rather than as two changes wearing one title.

## Steps

The verbs are the steps, and each refuses its own misuse. Yours, as the coder:

- `.meta/say/post comment <n> < body.md` — a comment on a pull request or an Issue
- `.meta/say/post notice <pr> <path> <line> < body.md` — noticed and not done: the marker and the mention supplied, held open for the solo
- `.meta/say/post answer <thread-id> < body.md` — answer: reply, then resolve; refused when this Actor is the thread's sole author, unless the reply links an Issue, which is what a promotion looks like (solorepo's DR-127) — and then the reply goes out and the thread is left open for a second Job
- `.meta/say/post resolve <thread-id>` — resolve a review thread whose answer or promotion link is already posted; refused for a thread only its caller's own Trailer speaks on, promotion link included — a second Job's to close, ordinarily the reviewer's run, which `move request-review` summons
- `.meta/say/post promote <thread-id> --title T [--difficulty D --mandate "<his words>"] [--no-resolve] < issue-body.md` — at approval: file the Issue with the Issue form's body, `challenge` alone for the reviewer to read unless the solo mandates a level, which a run may not hold and which `--mandate` quotes him asking for, reply with the link, resolve (or defer resolution) — always deferred where the promoting Actor is the thread's sole author, since resolving it too would be the only voice on the thread clearing its own hold, and a second Job closes it instead
- `.meta/say/post landed <pr>` — post what landed for every Challenge the body closes, rendered from the record
- `.meta/say/move waits <issue> --on <n>[,<n>]|--off <n>[,<n>]|--clear` — record or drop blockers on an Issue already filed: GitHub's blocked-by relationship and the `**Waits on.**` line together; refused on a blocker that is not an open Issue, on an Issue naming itself, on a cycle, and on a line whose prose cannot be safely rewritten
- `.meta/say/move claim <issue>` — take an Issue: assign it to this Role's account; refused to a session on a Challenge no reviewer has read, and at `easy` or `medium`, which are the loop's until the Issue is moved to `hard`
- `.meta/say/move stop <issue> < body.md` — where this Job stopped and why; the claim released, the Issue to the solo as `human`, the pull request left open
- `.meta/say/move obviate <issue> --by <issue|pr> < body.md` — close an Issue another answer overtook, as not planned, where each part of it went on stdin; the comment on the Issue and the backlink on what answered it, and the claim on the Issue left as it stands; refused unless `--by` names an open Challenge or a merged pull request
- `.meta/say/move open --title T [--base B|--on <pr>] [--draft] < body.md` — open a pull request, the form filled; --on opens a layer on that one and links the stack; --draft opens it as a draft, which the merge manager, advance and the reconciler pass over; move ready takes it out
- `.meta/say/move ready <pr>` — take a draft out of draft; refused while its branch changes no file against its base, so a plan-only pull request stays a draft (solorepo's DR-273)
- `.meta/say/move layer <pr> --on <pr>` — make an open pull request a layer on another
- `.meta/say/move revise <n> [--title T] [< body.md]` — replace a pull request's or an Issue's body, or its title; it does not change what blocks an Issue, which is GitHub's relationship and `waits`'s to set; the reviewer's for a Challenge whose first line it found wrong at reading
- `.meta/say/move supersede <pr> --by <pr|DR> < body.md` — close a pull request another answer to its Challenge overtook, the reason on stdin; refused unless what `--by` names has landed — a merged pull request, or a Decision the trunk adopted — and the body closes a Challenge, and every Challenge it closes is closed already
- `.meta/say/move merge <pr> [--stack|--auto]` — merge; a layer merges everything below it; --auto arms GitHub to merge when green
- `.meta/say/move merge-manager [--dry-run]` — evaluate open pull requests against semaphores, rank eligible candidates by leverage, assert choices and deferrals out loud, and squash-merge the top candidate
- `.meta/say/move reconcile [--live] [--dry-run]` — run the merge manager, then read every open Issue and pull request through the classifiers and perform what each is owed where no run is answering it — a rebase or review pass dispatched, a review requested again, a take dispatched, an unread Challenge re-delivered to the reviewer, a dead run's claim released; reported and not performed without --live
- `.meta/say/move request-review <pr> [--to R]` — hand off: request review from Role R's account, the reviewer's by default; refused on a branch GitHub reports as conflicting, which no review can run on
- `.meta/say/move mint [--concept <ident>]` — issue the next Decision number and reserve it on GitHub, so two branches cannot take the same one; `--concept` reserves a Concept of the Ubiquitous Language instead, named by the identifier its row will carry, the first of the three layers a new vocabulary row stands on, and it is refused to a run (solorepo's DR-276)
- `.meta/say/commit -m <subject> [--allow-empty] [< body]` — commit as this Actor; never `git commit`, which signs nothing
- `.meta/say/whoami` — which login this channel speaks as

A verb not listed is not yours to type. What no verb enforces:

1. **Open it when the work starts.** Never open a pull request when work is already finished. Written at the end it becomes a summary of the diff, which git already holds. For `easy` and `medium` Challenges, state the intended shape in the opening body, and review on the diff is the check; for `hard` and `human` Challenges, formulate the plan under **The plan.** and validate it with the solo before writing code, which is the bound that prevents unsound architectures from being enacted into diffs (solorepo's DR-249). On `hard` and `human` Challenges, modifying tracked repository files or running verification gates prior to opening the pull request via `move open` is strictly prohibited (solorepo's DR-269). A coder records the initial plan under **The plan.** in the pull request body on a zero-diff [[seed-commit|Seed Commit]] authored via `commit --allow-empty -m "Record initial plan for Challenge #<n>"` before writing code. The plan passes two gates before any code, and both are required (solorepo's DR-273): the solo's approval in session, which lets the coder go ahead under this Discipline and skips no step of it, and then the reviewer's approval of the plan on the pull request. Open that pull request with `move open --draft`, so that the merge manager, `advance` and the reconciler pass over it and an approval of the plan cannot merge the empty commit; nothing takes a branch that changes no file out of draft. The reviewer raises points on a plan-only pull request with `comment`, since there is no line for a thread, and an approval there approves the plan and not a merge. A plan that changes materially in answer to the review goes back to the solo before code. Once both gates pass, push the implementation, take the pull request out of draft with `move ready`, and request review again.
2. **Take Challenges in as pull requests.** Receive every Challenge as a pull request, whatever raised it — the solo, a scheduled job, another agent — and name the Challenge in the body with a closing keyword, so the merge closes it and nobody has to remember to.
3. **Raise a Challenge with the form.** Propose its level in the body rather than labelling it: `easy`, `medium`, `hard` or `human`, your guess at what it takes for the coder Role. The reviewer reads every Challenge before any coder takes it, and its verdict is the label — `move triage`, which lands the level the reviewer found after asking what the form asks and what only the tree can answer: a trigger or a cost that will land, a blocker on the first line, no mechanism already in the tree that answers it, and no decision owed, which is `human` whatever the effort (solorepo's DR-230). A loop takes `easy` and `medium` the moment the label lands, so the reviewer's act is what opens the door; `hard` is coder work too large for a loop, which waits for the solo and a session beside him; `human` is where what the Issue needs is the solo rather than a Job at all, which the next step is how to reach. A Challenge no reviewer has read is nobody's to claim. A level says who answers the Issue rather than how big it is (solorepo's DR-226), and the reviewer says it rather than the raiser, who is the one reader with a stake in the answer; the loop still corrects it downward only. The verdict names what it checked — worth doing, waits on, already answered, decision owed — and is posted on the Issue before the level lands, so a level landed without a reading shows as one. A level landed with the filing on the solo's say-so is the solo's verdict given in advance and skips the reviewer on purpose; a Job with no such mandate leaves the level to the reviewer, and a Challenge nothing has touched for an hour unread is a reviewer door that did not fire, which the sweep reports. A run cannot hold that mandate, because the solo is not beside it, and the verbs refuse it one: what it files and what it moves carries `human` or no level at all, the reviewer's own reading excepted, which is the verdict itself and is admitted by the account it speaks as rather than by the workflow it runs in (solorepo's DR-235). `human` is not the way round that — it starts no Job and asks for the solo, which is PR First's *Hand it back the moment the next step is not yours* step said at the moment a run finds a decision owed or work it cannot finish. The label is also what says whose a branch is: a session that takes up a pull request the loop holds has the solo move the Issue to `hard` first, and the loop's next pass stands down. Moved back, the loop answers the next verdict and not one already standing — a relabel fires the Issue door and re-delivers no review — so a verdict the session leaves behind is the session's to answer, or the solo's to dispatch, which is a verb of the channel like every other act GitHub records.
4. **Hand it back the moment the next step is not yours.** Any Role holding a Challenge may stop and give it to the solo — `move stop`, which says where this Job stopped and why, releases the claim, moves the Issue to `human` and leaves the pull request open for whoever takes it up. A Role that holds no Challenge says the same thing where it is standing rather than staying silent — the reviewer in its verdict or on the thread, naming what the solo must settle — and the Issue reaches `human` through whoever does hold it. The reasons are open and the bar is deliberately low (solorepo's DR-226). Two are examples rather than the rule: a loop that cannot finish what it took, and an Issue whose next step is a decision rather than an implementation, which is `human` the moment anyone notices one is owed, whoever is holding it and whatever its effort.
5. **Argue there.** Review, objection and answer belong where the next reader will look, not where one participant happens to be.
6. **Answer every thread and resolve it.** Resolve every thread after answering it, including one the diff has overtaken. Outdated is not answered: GitHub collapses a thread whose anchor moved and leaves it open, and a reader years later cannot tell a point that was addressed from one that was dropped. A reviewer's top-level comment on the pull request is a thread too, owed until it is answered with a `post comment` that links it (solorepo's DR-273): GitHub cannot resolve one, and a reply carries no reference to what it answers, so the link is what settles it.
7. **Title it with words someone will search for.** An index is worth exactly its titles, so choose words someone will search for.
8. **Reread the diff and notice.** Before you hand the branch over as finished, reread the diff against `origin/main` to verify quality and consistency — an in-session pass alike across harnesses (solorepo's DR-181). Raise what was noticed and not done as a **conversation on the diff**, at the moment it is noticed — not a bullet in the body, which closes with the pull request, and never a closing summary. The last comment is the one that counts, so replying without the marker is how an item the change has overtaken stops being parked, and an unresolved conversation blocks the merge, so nothing is walked past without somebody deciding what it is.
What you notice and *can* do, do. A fix the branch can already reach that is mechanical, owes no Decision, implies no Challenge of its own and is proved by the gate this change is already running is not noticed-and-not-done at all — it is an **Incidental Commit**, and it is made in a commit of its own whose subject begins `Incidental:`, rather than into a conversation that will cost another Job's start to answer (solorepo's DR-236). The prefix is the whole form and it is there to be counted: `git log --grep '^Incidental:'` is how a later reader tells whether this licence is being taken. All four parts hold or it is a notice: the bound is what keeps a licence to fix from becoming a licence to wander, and the coder is where that risk lives, since nobody else is reading yet.
9. **Promote at approval.** Never promote before approval. What survives the argument earns an Issue and the thread is resolved with a link to it; what the change overtook is answered and resolved where it was raised. Filing at review time creates a tracker item with no relationship to the outcome, which goes stale the moment the approach moves under it.
A thread every comment of which is this Job's own — which every notice is — gets the Issue and the link and stays open, because a resolve from its only voice is A16's falsifier rather than an answer to it (solorepo's DR-224). Closing it is a second Job's, and the next step is how one arrives: request review again, and the Job that answers it resolves what the promotion left open.
A point **another party raised** that survives and meets the Incidental Commit bound can be paid for here rather than later, and at approval that is the first thing to try: answer it with a **commit on this branch** before the merge, the reply naming the commit, and file no Issue (solorepo's DR-236). This adds no fourth answer to the three a point can get — it changes what *right, and a change to make* may be settled with when the point belongs to a different change.
Your own notice is not reachable by it, and the channel is what says so: the sole-author refusal stands, with promotion as its one exception (solorepo's DR-127), so a coder that decides its own notice is moot still can only hand it on. That is a floor rather than an obstacle — an item inside the bound should never have become a notice, since the step above says to fix it — and the way in is the reviewer saying on the thread that it is inside the bound, which makes the point another party's and the judgement one two Roles have made. This is the cheap case rather than the risky one — the reviewer is already reading, and a commit pushed before merge is re-reviewable where an Issue is a promise to reload the problem later. Promotion keeps everything the bound excludes: work owed a Decision, work the branch cannot reach, and anything whose size would make this change stop reading as one.
10. **Post what landed.** Record what landed for the Challenge before merging, generated and never typed: written by hand it is the copy that flatters, and complete whether or not the record was.
11. **Merged, never abandoned.** **Superseded** is the one exit that is not a merge. A pull request exists because a Challenge does, and a Challenge is a real need; work that turned out to be the wrong answer merges as the record of that, which is worth more than a closed tab. What cannot merge is work another change has already answered — the tree holds a different answer to the same Challenge, so the diff would install a second mechanism over a working one. That closes by `move supersede <pr> --by <what answered it>`, which is refused unless what `--by` names has landed — a merged pull request, or a Decision the trunk adopted rather than merely holds a number for — and unless the body closes a Challenge and every Challenge it closes is closed already: the closing is the evidence, so a change nobody superseded still has merge as its only exit, and so does one that names no Challenge at all. A Decision number the branch minted and never landed is not released with it — the tag is the allocation and nothing issues a number twice — but written back into the record as WITHDRAWN, which `supersede` names as it closes.
12. **Close by merge or obviate.** An Issue closes by the merge that names it, or by **obviate**, and never by hand. A Challenge split into others, or filed a second time under different words, is answered without a change of its own: the work is owned elsewhere and nothing is left here to merge, so the Issue sits open and `just next` keeps offering it as ripe. `move obviate <issue> --by <what answered it>` closes it as not planned, says on the Issue what part of it went where, and puts the backlink on what answered it, so the pair reads from either end. It is refused unless `--by` names an open Challenge or a merged pull request: an answer nobody is queued to give and one that never landed both leave the need with no open record, which is an Issue closed against nothing. Closed in the browser instead it is an act the record cannot see, which is what the signing hook refuses.
13. **Push before stopping, and stop at green.** The gate is an exit check for the Agency you hold, not an entrance check: `main` is evergreen, so do not run `just gate` at session start or against an unmodified checkout. Work that exists only in a worktree the next Job will never see has not been handed off, and a red gate is not a handoff — it is a mess whose author is gone. The gate is the completeness test for the Agency you hold; nothing else is.
14. **Bring a branch current by rebase.** Never update a branch with GitHub's plain **Update branch** button on the pull request page: it authors a merge commit with no `Actor` Trailer, which A19 refuses in the same words as a commit made by hand. **Update with rebase**, and the channel's own `advance`, write no such commit.
15. **Stack what waits on what.** A change that can only start once another lands is a **layer**: its own branch and pull request, based on the layer below and linked into a stack, so the layers merge from the bottom and GitHub rebases what remains.
16. **Request review.** Hand off by requesting review of the next Role's account. The request is the handoff's whole signal, and a note beside it pretends to be one.
17. **Read what GitHub holds on arrival.** On arrival, read what GitHub holds — the pull request, the diff, the commits, the threads and the check states. There is nothing else, by design. Ask what this branch already owns: one branch is one pull request, so the checkout is the token and GitHub resolves it. Authorship cannot answer this, since every pull request here is the solo's. The shape of the branch is itself a claim: `<harness>/issue-<n>` is the loop's, the number being how a later pass finds its Challenge across an event it did not see, and a session names its branch `<harness>/<slug>` instead, saying what the work is and never beginning the slug `issue-`. A branch that takes the loop's shape asks the loop to take the work, and it declines where the work is not its own — `held` at `hard`, `closed` where the Challenge it names is closed already, `stale` at no level a loop takes, `unnamed` where the ref names no Challenge — but it declines out loud, on the pull request, and that notice is a conversation the session then owns and its merge waits on.

## Where the judgement is

What constitutes one pull request. Too coarse and an argument has no subject; too fine and the record narrates change by change without ever saying what the whole was for.
Which Role to hand to, once there is more than one.
Whether a review comment is answered. A reviewer's point can be right, right about something else, or overtaken by the diff, and only the first is a change to make — but all three are owed a reply that says which, per A16. Resolving one to clear the gate is the shortcut the gate teaches.
And which observations earn an Issue. The test is whether you can say what would make it worth doing — a trigger, or a cost that will land. "This function is long" has neither. "This retry has no backoff, and it will matter the first time the endpoint is slow" has both. File everything and the tracker becomes the file it replaced, with better tooling.
And, before that, whether it earns an Issue rather than a commit. Topical fit is the wrong test standing on its own, because it asks what the change is about and not what ejecting will cost. solorepo's #624 was raised on a branch that was already editing one of the two files it needed and already re-rendering the other, and it was ejected because the record it had to edit belonged to another Decision; its delivery, solorepo's #626, was three additions and three deletions across those two files. An hour and a loop to move an identifier. Weigh the ejection against the impurity. The bound in the steps is a floor and not a licence — an item that fails any part of it is still a notice and still an Issue, and scope creep answered with "it was mechanical" is the shortcut this test teaches.
Whether a point turns on a fact about a system outside this repository — GitHub, a harness, a language, a library. If it does, the answer is a quote from that system's own reference or a test run against it, and a reading is not an answer whichever way it falls. solorepo's #117 closed one on recall twice, once each way, and the documentation took one fetch.
Whether a word in the change is doing the work of a domain term (per A17, solorepo's DR-190). If it is, it belongs in closed-world wikilinks `[[concept]]` and must resolve to an existing concept or wiki page, or be minted with the solo into the Ubiquitous Language with a corresponding Knowledge Management wiki entry. A word that arrived by use without minting is an objection to raise.
Whether the approach is the right one (solorepo's DR-249). A reviewer's first interrogation of a pull request is its root architecture, not merely whether the diff compiles, lints, and passes tests. An unsound plan rejected at the root costs a conversation; accepted into the diff, it costs a multi-hour cycle of incremental patches propping up an unviable foundation.
Whether a change to the loops adds a reader, a read-back, or a door where there is meant to be one place (solorepo's DR-264). The loops move toward one state model, one settling channel layer, and a scheduled reconciler, in that order, and a change that reads pull request or Issue state without asking the one classifier, reads back a write the channel should have settled, or puts logic longer than a call in a workflow's `run:` block is an objection to raise, whichever seam has landed. Where the seam that would answer it has not, the point is right about something else, and its reply links the Challenge that owns that seam, which is the one Issue every seam's coder reads before opening its pull request; the thread resolves on the link, as a promotion does.

**None of the below decides any of the above.** A script can tell you a thread
is unanswered, or a branch unpushed. What to write, and whether a point is
right, is yours.

## The body

Fill this in when the work **starts**. `check_pr.py` reads the same form, so a
heading added here is required by that act alone.

```markdown
## <a title someone would search for>

**What this changes.** The shape of the change. Not the file list; the diff has that.

**The plan.** For a `hard` or `human` Challenge, the approach validated with the
solo before code: the architecture chosen and what was rejected. "Not applicable
— `easy`/`medium`." is a complete answer.

**What the ground looked like.** The context that will not be visible from the
code afterwards — what was already true, what was tried and abandoned, what
constraint made the obvious approach wrong.

**What would make this removable.** The condition under which this comes out
again. "Nothing would" means it is load-bearing forever, and that claim needs its
reason stated.

**What was decided.** One link per item, to a DR. A decision taken inside a
change belongs in the same change; recorded afterwards, it is a decision only
its participants could cite for as long as the gap lasted. "None." is a complete
answer and often the true one.

- DR-<nnn> — <the question that demanded an answer, in one line>

**What it closes.** One item per Challenge this pull request finishes, written
with a closing keyword so the merge closes the Issue and nobody has to remember
to. "None." is allowed and is a question: PR First says a pull request exists
because a Challenge does.

- Closes #<n> — <the Challenge, in one line>

**What was noticed and not done.** One link per item, to an Issue, filled in at
**approval** — these are the conversations that survived the argument. Empty until
then, and often empty for good: an item the change overtook is answered in its
thread, not tracked.

- #<n> — <one line, so the list is readable without opening anything>
```

## What is checked

- **A15.** Work noticed and not done, recorded only in a summary, has not been noticed.
- **A16.** A review thread resolved without an answer has not been resolved.
- **A18.** Work not pushed has not been handed off.
- **A19.** A commit that does not name its Actor is unattributable.
